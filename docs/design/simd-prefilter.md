# Production CRS prefilter and Hyperscan backend

> **Historical research report.** This records the state of the branch/commit
> below. The prefilter remains opt-in, but the default request-inspection
> backend is now the native Rust engine, not Coraza. For current behaviour see
> [engine selection](../user-guide/engine-selection.md).

**Status:** production-ready within the non-default `hyperscan-eval` feature.
**Worktree:** `.worktrees/simd-prefilter`.
**Artifact:** `rules/crs/prefilter.json` (schema v1), unchanged.
**Library:** Vectorscan `5.4.12` (`libhs`, nixpkgs `vectorscan`).
**Target:** 0.74 ms p50 for a 4 KiB form body (engine-kernel reference).

## 1. Audit: why the prefilter was not in the default request path

The prefilter was already compiled once per process (`Prefilter::embedded` uses
`OnceLock`), but the Hyperscan path was only exercised by the standalone
`hyperscan-bench` binary. Nothing in the request path constructed a shared
Hyperscan database: `src/waf/fastpath/body.rs` and the gated host path call
`Prefilter::evaluate`, which only ran the 84 Aho-Corasick automata. The costs
that kept it out of the default path were:

* **Per-group extraction.** The Aho-Corasick path calls `apply_pipeline` once
  per group (4 extraction variants × 21 transform chains). The extraction and
  transform work is repeated for every group even when the transform chain is
  a no-op.
* **No shared matcher.** Hyperscan databases were compiled in the benchmark
  process only, and the scanner owned a single scratch region (not `Sync`), so
  it could not be shared safely across async workers without serialising.
* **No cheap group skip.** Every group scanned every representation even when
  a group's literals could not occur in that view.
* **No bounded fallback.** A Hyperscan compile failure or unsupported CPU had
  no defined production fallback; the benchmark would panic.

The prefilter remains non-default because the artifact gates only 62 of 113
body-relevant CRS entries; `@detectSQLi`, `@detectXSS` and the size/validation
rules stay ungated. The prefilter is an accelerator, not a Coraza replacement.

## 2. Production design

### 2.1 One compilation, shared across workers

`SharedHsDatabase` owns an immutable `Arc<DatabaseHandle>` and a
`Mutex<Vec<ScratchHandle>>` pool capped at 64 idle scratches. Hyperscan permits
concurrent scans against one database; the scratch region is the only mutable
state, so each scan borrows a scratch and returns it. The compiled set is built
inside `Prefilter::from_artifact`; `Prefilter::embedded` caches the whole
prefilter in a process-wide `OnceLock`, so production callers pay the ~235 ms
compile once at first use and then share the same `&'static Prefilter`.

### 2.2 One extraction per representation

The Hyperscan backend is keyed by transform chain only. For each input value it
applies each of the four extraction variants once, then scans the same view
against every chain. Transforms that are provably the identity on the view are
skipped by the existing conservative predicate. This is the same soundness
contract as the per-group Aho-Corasick path, with less repeated work.

### 2.3 Group skipping

Each compiled group carries a `required_byte`: a byte present in every literal
of the group (with ASCII case expansion for case-insensitive literals). If the
scanned representation does not contain that byte, no literal in the group can
match and the scan is skipped. The check is conservative: a hit only means the
group might match. Groups whose literals share no byte are always scanned.

### 2.4 Bounded fallback

If the feature is disabled, `hs_valid_platform()` rejects the CPU, compilation
fails, or a scan returns an error, `Prefilter::evaluate` and
`evaluate_inputs` fall back to the pure-Rust Aho-Corasick groups. The fallback
is bounded by the input length and is the same code path used by the default
`crs-prefilter` build. `hyperscan_error()` exposes the reason for diagnostics.
No fallback recurses; a failed Hyperscan scan runs the Aho-Corasick path once.

## 3. Benchmark results

Generated by `scripts/bench-prefilter.sh` on the shared host (release,
`LTO=false` to keep the build bounded; 20 reps, 3 warmups). Absolute numbers
move with host load; the ratios and the comparison with the 0.74 ms kernel
figure are the useful signal.

### 3.1 Production prefilter (all four extraction variants)

| body | Hyperscan p50 | Hyperscan p95 | Aho-Corasick p50 | Aho-Corasick p95 | HS/Aho |
|---:|---:|---:|---:|---:|---:|
| 1 KiB | 59.8 µs | 63.2 µs | 48.4 µs | 49.2 µs | 1.24× |
| 4 KiB | 215.4 µs | 256.8 µs | 185.0 µs | 222.1 µs | 1.16× |
| 8 KiB | 421.0 µs | 455.7 µs | 364.6 µs | 369.6 µs | 1.15× |

After rebasing onto main the pure-Rust path uses a union automaton plus the
shared transform cache, and it is now **faster than Hyperscan** for the sound
all-extraction scan (HS is 15–24 % slower). The production `Prefilter::evaluate`
scans all four extraction variants because the body processor is not known at
the prefilter boundary. Content-type-aware extraction (`hs-fast` in the raw
benchmark) is **13.6 / 47.9 / 94.5 µs** at 1/4/8 KiB, which is where Hyperscan
wins, but it is only valid when the caller knows the body processor.

### 3.2 Cache and compile

| metric | value |
|---|---:|
| `Prefilter::embedded` cold (first call) | 154.0 ms |
| `Prefilter::embedded` warm | 2 ns/call |
| integrated Hyperscan compile | 184.5 ms |
| Aho-Corasick compile | 22.4 ms |
| Hyperscan databases | 18 chains, 3 247 patterns, 1 250 KiB |

The cold number includes the one-time Hyperscan compile; warm calls are a
pointer load from the process-wide `OnceLock`. On an uncontended host the
compile is ~235 ms (see `hyperscan-evaluation.md`).

### 3.3 Prefilter + engine against the 0.74 ms kernel figure

The prefilter runs before the engine, so the end-to-end cost is additive. Using
the published engine-kernel p50 (189.69 / 741.28 / 1 740.08 µs at 1/4/8 KiB):

| body | prefilter (all extracts) | + kernel | prefilter (content-type) | + kernel |
|---:|---:|---:|---:|---:|
| 1 KiB | 59.8 µs | 249.5 µs | 13.6 µs | 203.3 µs |
| 4 KiB | 215.4 µs | **956.7 µs** | 47.9 µs | **789.2 µs** |
| 8 KiB | 421.0 µs | 2 161.1 µs | 94.5 µs | 1 834.6 µs |

At 4 KiB the all-extraction prefilter plus the 741 µs kernel is **0.96 ms**,
about 1.29× the kernel-only target. Content-type-aware extraction brings it to
**0.79 ms**, 1.06× the target. The prefilter adds 48–215 µs at 4 KiB. The kernel
remains the dominant term; the prefilter only pays off when it removes enough
gated rule work to offset that addition.

### 3.4 Attack bodies and parity

First-hit attack bodies are 0.3 / 0.5 / 0.6 µs at 1/4/8 KiB (Hyperscan,
content-type extraction), versus 54.4 / 173.8 / 330.0 µs for the full
Aho-Corasick union scan. Attack traffic is where the hardware matcher wins. The
51-case corpus has 36 hits on both engines, **0 Aho-only and 0 Hyperscan-only**
hits.

## 4. Where time goes

* **Clean bodies:** extraction and transform work dominates. The raw Hyperscan
  scan is 0.2 / 0.5 / 0.8 µs at 1/4/8 KiB, while the sound all-extraction
  prefilter is 59.8 / 215.4 / 421.0 µs. Content-type-aware extraction drops that
  to 13.6 / 47.9 / 94.5 µs, so the four extraction variants are roughly 4× the
  work. Main's union automaton plus transform cache makes the pure-Rust path
  faster than Hyperscan for the all-extraction case; Hyperscan only wins when
  the body processor is known.
* **Attack bodies:** first-match termination keeps the scan at sub-microsecond
  latency (0.3 / 0.5 / 0.6 µs), far below the full union scan. Hyperscan reports
  the first matching pattern, so the boolean path exits early.
* **Compilation:** ~185 ms once per process for 18 chain databases (~1.25 MiB);
  warm `Prefilter::embedded` calls are 2 ns. The Aho-Corasick fallback builds its
  union automata in ~22 ms and remains available without `libhs`.

## 5. Regression coverage

Unit tests cover literal hit/miss, anchored and unanchored literals,
case-insensitive matching, UTF-8 literals, empty and 1 MiB inputs, the shared
database's thread safety, `first_only` vs all-match scans, and parity between
the Hyperscan backend and the pure-Rust fallback on the same bodies. See
`src/waf/prefilter.rs` and `src/waf/hyperscan.rs`.

## 6. Limitations

* After the main-branch union-automaton and transform-cache work, the pure-Rust
  prefilter is faster than Hyperscan for the sound all-extraction scan. The
  Hyperscan backend is retained for content-type-aware callers and attack
  first-hit latency (sub-microsecond), but it should not be enabled as the
  default all-extraction matcher without a content-type dispatch.
* Hyperscan databases are platform/feature-set specific; this build compiles at
  first use rather than serialising a cache. A future optimisation can key a
  serialized database by CPU features.
* The prefilter cannot withhold the body on stock CRS because 51 body-relevant
  entries are ungated. Gated mode removes only rules whose mandatory literals
  are absent; Coraza remains the decision maker.
* The production integration is behind `hyperscan-eval`; `crs-prefilter` alone
  keeps the Aho-Corasick path and no defaults changed.
